# 按模块顺序实施的计划

供 `deephelp-module-planner` 和实施会话使用。模块规格在 `docs/MODULES/`，实施优先级见 `docs/ROADMAP.md`，分支交付见根 `AGENTS.md`。M 编号是能力目录；“完成Mxx”覆盖该M全部特性，由同一会话、同一主写者顺序完成，每个特性独立验收与分支交付。用户明确只选一个特性时才按单特性范围停止。

## 读取与判断

1. 记录分支、HEAD 和未提交差异；读 AGENTS、PROJECT_STATE、ROADMAP。
2. 读当前模块、直接前置 handoff、相关代码/测试；接口变化再读 CONTRACTS。
3. SDK/真实服务能力未知时先做最小探针；已有成果先核验，不重建。
4. 有来源争议才核对 SOURCE_MAP、文件哈希和 PDF 页图。无法核对就标来源未验证，不补造事实。

保留工具可识别的四种判断：`DIRECT`（直接做）、`DECOMPOSE`（列多个顺序特性）、`PROBE_FIRST`（先探针）、`VERIFY_EXISTING`（核验已有实现）。`DECOMPOSE` 不代表多 Agent 并行，也不要求 S 文件。

## 唯一计划文件

每个 M 只维护 `planning/Mxx/PLAN.md`。已有适用文件原位更新，不补建空文件；完成后删除已被规格/handoff覆盖的重复步骤，保留未完工作与独立设计并修正链接。普通计划用下面五项即可：

1. **这次做成什么**：一句话目标、可演示输入/输出、范围外事项。
2. **从哪里改**：复用接口、预计改动路径、依赖/迁移影响。
3. **怎样证明**：正常路径、关键失败路径、实际检查命令；先按ROADMAP决策表选择离线/针对性live/明确完整评测。live写样本理由、预期调用/token范围、含复验余量共享上限和无需重验依据；不自动重复历史模块或四能力探针。
4. **什么时候停**：整个M全部特性完成、合理运行上限、前置未满足、验收失败、无法恢复的真实依赖问题与授权外动作；用户限定单特性时按该范围停止。常规模型选择及参数按AGENTS自行落实，以学习效果为先。
5. **怎样交付**：feature 分支名、合并条件、受影响 handoff/STATE；未完成事项。

模块确实需要多个特性时，只在同一 PLAN 中列出全部范围、顺序和各自验收边界，逐项建分支；每项交付后继续同一M的下一项，不要求用户逐项另启。不要凑固定数量，不为接口、实现和测试分别建“任务包”。探针结果会改变实现时，结果出来前不预写整套后续细节，结果出来后原位更新PLAN并继续。

## 完成条件

计划中的命令不是通过证据。纯离线特性可用离线验证验收；依赖真实 API/中间件的特性，真实检查失败或未执行就保持未完成，不合并、不继续依赖它的特性。只有规格内全部特性通过适用验收并完成交付，才可报告整个M完成；首项探针或单特性交付只代表对应范围通过。测试要求以 ROADMAP/AGENTS 和当前特性为准，不自动把 unit/integration/live/e2e 每层都写成必做。

规划阶段不实施业务代码、不创建 handoff、不自动 commit/push；用户明确要求提交规划时按AGENTS交付已校对文档。实施交付遵守 AGENTS。对用户报告模块目标、全部顺序特性、停止条件和改动文件，不要求用户理解工具内部枚举。

用户2026-10-05追加的M32–M36复用此计划格式：结构/清理须有实际职责映射和用途/引用证据，课程须有可运行实验/Java类比边界/关键注释，前端须有实际机制与数据来源/状态/中文指引。规格/PLAN可多模块一次交付，但一个M仍只有一份PLAN；不得把未执行的删除、课程、免登录或框架页面报告为已完成。

M37–M39按用户2026-10-05收窄后的最终学习范围规划：M37本地核心教学与云端完整体验分别验收，不要求双环境完全一致或本机全栈；M38主要给Python/Agent需要解释的代码补通俗详细中文注释并局部收口职责，排除前端/数据JSON注释任务；M39仅删除不必要文件并修正直接引用，不附加部署/重构/文档重写。复用已交付M32–M36，按真实缺口形成顺序特性。规划提交不等于启动实施，后续按用户明确启动范围执行。

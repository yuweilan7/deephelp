# 一次特性的实施计划

供 `deephelp-module-planner` 和实施会话使用。模块规格在 `docs/MODULES/`，实施优先级和分支流程在 `docs/ROADMAP.md`。M 编号是能力目录；一次只做一个特性。

## 读取与判断

1. 记录分支、HEAD 和未提交差异；读 AGENTS、PROJECT_STATE、ROADMAP。
2. 读当前模块、直接前置 handoff、相关代码/测试；接口变化再读 CONTRACTS。
3. SDK/真实服务能力未知时先做最小探针；已有成果先核验，不重建。
4. 有来源争议才核对 SOURCE_MAP、文件哈希和 PDF 页图。无法核对就标来源未验证，不补造事实。

保留工具可识别的四种判断：`DIRECT`（直接做）、`DECOMPOSE`（列多个顺序特性）、`PROBE_FIRST`（先探针）、`VERIFY_EXISTING`（核验已有实现）。`DECOMPOSE` 不代表多 Agent 并行，也不要求 S 文件。

## 唯一计划文件

每个 M 只维护 `planning/Mxx/PLAN.md`。已有文件原位更新；旧 S 文件仅作为已有任务参考，不继续拆分，不补建空文件。普通计划用下面五项即可：

1. **这次做成什么**：一句话目标、可演示输入/输出、范围外事项。
2. **从哪里改**：复用接口、预计改动路径、依赖/迁移影响。
3. **怎样证明**：正常路径、关键失败路径、实际检查命令、必要的真实验证。
4. **什么时候停**：目标与预算、真实依赖失败、哪些动作不在授权范围。
5. **怎样交付**：feature 分支名、合并条件、受影响 handoff/STATE；未完成事项。

模块确实需要多个特性时，只在同一 PLAN 中列顺序和各自验收边界，每次选一个建分支。不要凑固定数量，不为接口、实现和测试分别建“任务包”。探针结果会改变实现时，结果出来前不预写整套后续计划。

## 完成条件

计划中的命令不是通过证据。纯离线特性可用离线验证验收；依赖真实 API/中间件的特性，真实检查失败或未执行就保持未完成，不合并、不继续依赖它的特性。测试要求以 ROADMAP/AGENTS 和当前特性为准，不自动把 unit/integration/live/e2e 每层都写成必做。

规划阶段不实施业务代码、不创建 handoff、不自动 commit/push。实施阶段按用户已指定的 feature → main → push 流程完成。对用户只报告目标、首个特性、停止条件和改动文件，不要求用户理解工具内部枚举。

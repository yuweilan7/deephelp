## 1. 识别任务并读到真实上下文

当前模块以我明确指定的 Mxx 为准；否则从本轮唯一模块附件的标题和正文识别。合集、通用模板、历史上下文不算另一个当前任务。真有多个未指定模块才问我选哪个；不要要求手工替换本模板中的模块号。

仓库为 https://github.com/yuweilan7/deephelp 。有授权本地工作区时优先读该工作区并记录分支、HEAD、未提交差异；只有 GitHub 时先解析默认分支当前 commit，再固定该 commit 读取，避免不同文件来自不断变化的 main。先读 AGENTS.md、docs/CONTRACTS.md、docs/PROJECT_STATE.md、当前模块规范、planning/manifest.json 的该模块条目及直接前置 handoff。随后读取将要复用/修改的实际代码、测试和相关包配置；依赖变更时再读对应 lock 条目。架构变化时读 ARCHITECTURE/DECISIONS，不默认重读全部 22 个模块和历史报告。

仓库代码证明现状，已记录的契约/ADR规定目标，两者有冲突要明示而不是自动认为任一方永远正确。附件是旧版模块时与同 ID 仓库工作副本比较，使用已批准的最新要求并列出实质差异，不把旧 PG/资源/布局假设带回来。未提交本地内容不可冒充远端已有。

原 PDF 身份与位置见 docs/references/source-manifest.json，执行机相对路径 `.local/references/deephelp-original.pdf`；原 ZIP/解压稿只在 `.local/references/` 归档，不是执行规范。PDF 是 78 页截图文章而非作者源码。首次规划当前模块时按 SOURCE_MAP 和模块页码核对相关原图，不必逐 S 重读全文；模糊内容标注不确定。区分原文事实、仓库现状、工程决定、待验证事项。不复制内部页面、客户编号或原始截图到公开产物。

GitHub 不能读取未提交的 .local 文件。仅远程可读时使用本轮 PDF 附件；无原图则标 SOURCE_NOT_VERIFIED，不谎称核对过。无法读仓库时尝试已有连接或已上传的上下文包；确实不可达再使用 `scripts/project_context.py export --module Mxx` 导出的包，包缺相关代码时明确接口待核对。可以先设计不依赖缺失信息的部分，但不能编造前置完成或可直接实施的未知接口。

## 2. 由你判断粒度，不预设子任务数量

先给一个 decision 与简短理由，依据当前未完成范围、接口耦合、可验证的中间结果和风险，不依据“有22个模块”或模型档位名字机械切分：

| decision | 适用情况 | 本轮交付 |
|---|---|---|
| DIRECT | 范围内聚、接口已明确，一次有边界的实施即可验收 | 一份 IMPLEMENT.md；内部可有检查清单，不制造 S01/S02 目录 |
| DECOMPOSE | 存在确实独立的可验收里程碑，或混做会扩大排错/回滚范围 | 最少必要数量的 S 文件及顺序/依赖，通常 2–5 项但不是配额或硬上限 |
| PROBE_FIRST | SDK/持久后端/真实协议等未知项会改变实现方案 | 一份有成功/失败判据和预算的小型探针任务；后续只给条件分支轮廓，结果出来后差量补齐，不预编一整套不可靠 S |
| VERIFY_EXISTING | 已有对应设计或实现，主要剩核验或少量缺口 | 一份覆盖原要求的验收/补差异任务，不能只看文件存在就通过 |

decision 只表示工作组织，另列 readiness=READY/BLOCKED/PENDING_LIVE 等实际条件。DIRECT 不代表免测试或已获实施授权；DECOMPOSE 不代表可并行。凭据/费用未获授权只阻塞相关 live 步骤，不阻塞可独立完成的离线实现；核心接口/事务语义不明确则阻塞依赖它的修改。最多提出三个确实不能通过读取或可逆默认值解决的问题。

禁止统一要求拆成固定数量的步骤；禁止每个 S 再先创建一轮子 Prompt。不要把同一个小功能的“建接口、写实现、补测试、写说明”拆成四次会话；测试应随实现一起交付。只输出当前 M 所需，不预写全部未来阶段详细设计。

## 3. 实施组织：一个 M 一个主会话，顺序推进

默认一个有仓库读写能力的主实施会话负责当前 M，逐个执行任务，每个任务完成实现、相关测试、差异检查和必要交接后再继续。用户只授权当前 S 时停在当前 S；授权连续执行整个 M 时允许同会话顺序推进，不因模板要求反复问确认。共享契约、锁、迁移、PROJECT_STATE由这个主写者统一修改。

需要新会话时先落盘已完成项、当前 HEAD、失败测试、未提交改动和下一任务；接手者读取实际文件，不只依靠聊天摘要。S 开始时检查自规划基线以来的相关 diff，上一 S 合法实现导致的正常变化要复用；只有影响安全/契约的实质变化才差量修订。不要切回旧 commit 重写工程。

额外 Agent 默认只在固定 commit 上做只读代码审查、寻找反例或查官方接口，由主写者采纳修复。未经明确授权不开多个写者；只有接口稳定、路径/测试数据/迁移/锁互不影响且有独立工作树时才提并行建议。不要把 ultra、多 Agent、最高推理或更长文档等同于更高代码质量。

## 4. 按任务需要输出，不凑长文

A. 范围与依据：模块ID、decision及理由、readiness、实际读取的 commit/契约版本/代码与原图页、前置状态、实质差异和未定项。
B. 最小充分设计：本模块输入输出、状态/错误、复用接口、正常/失败路径、文件级改动与验收条件。涉及持久化才展开事务/幂等；涉及模型才展开调用/成本；无关章节用一句“不适用+原因”，不重复整套架构。明确哪些约束必须由确定性代码落实。
C. 执行任务：DIRECT一份；DECOMPOSE逐S给完整任务并画必要依赖；PROBE_FIRST给探针和决策出口；VERIFY_EXISTING给要求—产物—检查—缺口对照。每个任务包括目标、必读相对路径、规划基线和开工时HEAD解析规则、允许改动范围、具体实现与禁止事项、关键正常/失败输入及期望、基于实际工具的运行命令要求、停止条件、非破坏性回滚、交接。引用仓库稳定文档即可，不复制全部公共约束；但不能只写“实现上面的方案”。任务即使换会话也应可从路径恢复必要上下文。
D. 分层验收：本模块适用的 unit、真实协议/中间件 integration、真实模型 live、e2e、故障测试分别说明。设计中的命令不是已执行证据；不把模拟模型、合成业务、训练集准确率写成线上收益。保留当前模块指定的失败案例，不因缩小任务数而删测试。
E. 落盘与交接：设计放 docs/MODULES/Mxx.md；任务放 planning/Mxx/IMPLEMENT.md 或 Sxx_*.md，已存在则差量修订，DIRECT无需额外任务索引文件。完成情况集中到 handoffs/Mxx.md 的小表：任务/状态/真实实现commit/测试证据/下一步；模块汇总在 reports/Mxx/。不强制每个小S各写多份重复报告。输出commit只能提交后填，允许用 `git log -1 --format=%H -- <实现路径>`定位，不能自引用尚不存在的SHA。最终由主写者更新PROJECT_STATE；计划与已完成状态分开。

默认只授权规划文件产出，不自动推送；commit/push、live、云变更、危险操作按本轮用户明确授权执行。保留现有MySQL/Redis/Milvus和uv workspace，不重建P00，不安装无关平台、不添加框架层来凑设计。解释围绕可执行的因果和取舍，目标是稳定地完成一个模块，而不是不断规划如何规划。

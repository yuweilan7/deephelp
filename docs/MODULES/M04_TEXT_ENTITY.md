# M04｜文本清洗、并行实体提取与规则前置

**阶段：** B 最小闭环

**前置：** M02, M03

**来源：** 原 PDF 文件页 19–24、31–35、53。以下未由原文给出的实现细节均为本复刻方案的工程要求。

## 本模块目标
复刻输入校验、清洗/实体提取并行，以及规则→较轻模型→强模型的逐层补齐机制。关键是数据保真和可解释失败，不是尽可能多调模型。

## 按原图拆开职责
保留 raw_text；清洗产生 cleaned_text；实体提取形成带 value、span/message、source、confidence_kind 的字段。订单号、券号、SKU 等按字符串处理，保留前导零。原文 p21–24 提供分层阈值示意，但不能当现成校准值。规则匹配高确定性字段；仅为缺失或冲突字段调用模型；较低可信结果不能覆盖已确认字段。没有可靠值返回 null/needs_clarification，不猜。

原文 128 字符截断在本项目改成显式可配置策略：先提取保真关键实体、保留原文，超长时做有上限的裁剪/分段，不无条件丢掉后半段的订单和否定信息。中文全半角、空白、表情、拼写可规范化，但“未收到”“不是这个订单”“以前有优惠现在没有”、日期/金额/数量不能被清洗改义。

规则引擎不要凭宽泛关键词直接确认高风险意图。“退款到账了但金额不对”不能只因退款二字走简单退款 SOP。给规则加条件、排除项、优先级、命中证据与版本，命中不够明确就放行给后续识别。

## 本机模型与 API 的取舍
本轮默认 Regex+API 受限结构化提取；小模型端口保留但不部署本地 7B。后续个人电脑可插入本地模型对照。这个替代必须记在 ADR：复刻分层策略，不宣称复制原文的本地推理时延。外部 API 不按原图 200ms 成功预算设计；根据真实延迟与全链路 deadline 决定是否继续，超时返回未解析字段。

并行任务只并行独立清洗/提取，使用 M01 的 cancellation/超时方式。相同字段结果需确定性合并，不能最后写入获胜。输出 demand_type（main/supplement/new_topic/unknown）供 M11 使用，这只是话语功能判断，不等同最终意图分类。

## 验收数据
至少覆盖长文本尾部订单号、多订单、多券、否定反转、前导零、全半角、用户更正、仅提供订单号、空输入、恶意指令、模型输出不存在的字段、规则和模型冲突、API timeout。要求实体有证据来源，清洗不导致关键事实变化；各层命中率、模型调用数、延迟分开输出。

交付 TextCleanResult、ExtractedEntity、RuleMatch 的具体兼容接口、版本化规则、小型黄金样本、故障测试和 trace 事件。禁止把实体提取写成一个没有校验的“请帮我抽取”大 Prompt。

## 接口与分期边界

清洗/抽取可以生成 RuleMatch 候选与话语功能标签，但不在300阶段确定最终主意图并路由 SOP；规则决策在600统一消费。新结果必须带来源；明确更正与普通冲突区分，低可信结果不能覆盖已确认实体。先用现有 Regex/API 方案，不为补齐层数再接一个未经验证的小模型。

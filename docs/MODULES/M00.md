## 3. 最重要的设计裁决与因果

### 3.1 先适配已有工程，避免环境重建

旧包的PostgreSQL与4GiB假设不再有效，当前MySQL和5GiB Milvus实验已在仓库。选择保留，是避免两个数据事实源、浪费已经验收的隧道/资源配置，不表示MySQL天然更适合所有Agent场景。持久checkpoint另设门禁，不能借保留MySQL之名假定支持已解决。

首个业务workspace成员承载domain/application/adapters。逻辑分层不等于多个发布包；22阶段是开发顺序，不是22服务。这样保留既有root workspace而不提前制造跨包复杂性。

### 3.2 13段流水线与责任固定

源图p57给出13段，而p19概述12步，采用更细的p57作为工程基线并保留冲突记录。完整职责和短路路径在ARCHITECTURE第3节。M08先passthrough聚合、规则+Dense决策、只读SOP和模板回复；不是假装全部高级能力已经实现。

500输出有证据的current_event_context，600才进行一次主级联；700检查决策，800检查槽位，900固定SOP，1000只执行。此分工防止多个模型各说一次意图，导致步骤不一致和调用失控。

### 3.3 状态：业务问题、消息和执行不是同一对象

同session允许多个question；一条更正消息是新的message和run，但可以更新原question的实体版本。相同订单也能有两类诉求，不以order_id替代question_id。歧义补充不强制归属，返回CLARIFY并保留消息。

WAITING_SLOT是业务问题状态，本轮run可以SUCCEEDED且返回CLARIFY；没有需要长时间占用的执行线程。WAITING_APPROVAL才持久暂停原run，恢复入口必须显式确认权限和原operation计划。任何普通“好的”都不具有批准其它run的效力。

### 3.4 外部副作用与恢复

每项写操作先在MySQL登记PREPARED，固定operation_id、工具/参数hash、审批绑定；真正发出前验证批准和版本。网络调用不在长事务中。返回成功后落结果与outbox；若返回丢失则UNKNOWN，对账查询优先。只有下游确认未执行/失败且仍获授权，才可能重试同幂等操作。

checkpoint可能重跑节点开头，所以不能在interrupt之前夹带不可幂等写入。恢复需查业务ledger；已成功操作只能复用结果，不能再发一次。缺少可查询/幂等的下游时退出自动写流程，而不是承诺exactly-once。

### 3.5 模型不能负责的事

确定性代码必须负责身份来源、tenant/user过滤、请求幂等、实体版本冲突、状态转移、SOP/工具白名单、参数Schema、审批绑定、调用预算、响应证据校验。模型产生候选和解释，无法自行放宽这些约束。

外部数据中的“忽略规则”“退款成功”等文本只是数据，不能成为权限或完成证据。最终回答由事实对象生成；润色失败回退模板，不把故障写成成功。

## 4. 三个强制走查

### 场景A：订单信息更正

合成身份tenant-demo/user-a/session-1。m1：“订单DEMO-A没有享受优惠。”生成q1/r1，order_id=DEMO-A，entity_version=1。m2：“说错了，是订单DEMO-B。”是新消息与r2，但明确更正应路由q1，不把两单并列拼接。更正事件引用m1/m2，当前order_id=DEMO-B、question/version递增，旧证据保留。

若已有针对DEMO-A的待批准operation，参数hash和question_version不匹配，应REVOKED/APPROVAL_INVALID，不能把旧审批套到DEMO-B。更正路由含糊或订单归属不合法时先澄清/拒绝，不用LLM自信覆盖。M02检查provenance与版本，M04实体保真，M10生命周期，M11归属，M15审批失效。

### 场景B：双问题交错

m1：“我的优惠券不能用。”→qA等待券/订单；m2：“另外，订单DEMO-B参加了什么活动？”→独立qB；m3：“刚才那个券是COUPON-001，订单DEMO-A。”→补充qA，不是最近的qB。

期望两个question，qA包含m1/m3、qB包含m2；DEMO-A不能被union传递边并入DEMO-B；模型证据不足则m3暂不绑定question并CLARIFY。600仅对已选的当前事件调用一次主分类。测试同时覆盖同一订单两种诉求、不同用户相同订单字符串、已解决旧事件与新问题高相似。

### 场景C：审批后重放

M15之后的合成写工具op-demo-1，qC/rC，批准绑定参数hash H、SOP v1、question v3。恢复时再次校验授权/期限/版本，然后用op-demo-1作为下游幂等键调用。下游已成功，进程在账本落成功前崩溃。

再次resume不能再发权益：先按op-demo-1查询下游，成功则补写ledger/outbox与响应；未知则继续对账/人工，不盲目重试。两个审批者并发最多一个批准状态迁移成功；参数变更、SOP变更、批准过期均不得执行。验证的是“效果计数1”，不要求网络请求计数恰好1；状态查询可以有多个。

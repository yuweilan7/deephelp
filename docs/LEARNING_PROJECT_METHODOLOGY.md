## 摘要：真正被搭建起来的，不只是一套代码

DeepHelp 最值得复用的做法，不是某一句神奇 Prompt，也不是让最强模型一直工作，而是把复杂任务变成了一组可以接手、验证、恢复和理解的工程单元：先明确复刻什么，用 P00 排除环境不确定性，以 M08 为首个纵向闭环；再让实施会话按模块推进，用代码、测试、提交和 handoff 传递状态；阶段性重新审查结构、教学入口与过程文件，而不是无止境地添加功能。

这套方法已经表现出三个相互关联、但不能混为一谈的闭环：

| 闭环 | 真正的终点 | 不能替代它的东西 |
|---|---|---|
| 工程闭环 | 行为实现、适用验收通过、结果进入目标分支、状态可恢复 | 模型说“完成了”、一次 HTTP 200、单个探针通过 |
| 协作闭环 | 下一个会话知道做什么、做到哪里、遇到什么问题、从哪里续跑 | 完整聊天历史、只写一个 DONE、单纯定时触发 |
| 学习闭环 | 人能解释结果、预测反例、修改机制、验证迁移 | 项目规模、课程数量、通过测试的数量、AI 已理解 |

本次评价：**作为学习型项目资产，88/100；作为问题负责人表现出的人机协作能力，91/100。** 这是基于证据的主观量表，不是行业排名，也不是对作者个人知识掌握程度的考试成绩。项目已经有很好的教学底座；下一阶段的关键，不是继续把 M 的编号推高，而是把已经生成的系统转化成作者能独立运用的能力。

## 三、0 到 1：先建立可验证的理解，再建立代码

### 3.1 从 PDF 提取机制，不从截图机械复制系统

DeepHelp 的起点不是“上传 PDF 后做一个问答机器人”，而是复刻其中的客诉处理机制：意图识别、归属、记忆、SOP/MCP、可恢复执行、评测与反馈。内部平台、业务数据、供应商实现和训练素材不完整时，应该保留职责与可验证语义，用显式的工程替代和合成场景实现，而不是假装复原了源系统。

复刻前应形成一张最小来源表：

| 来源说了什么 | 必須理解的机制 | 本项目怎样实现 | 没有证据的部分 | 验收观察 |
|---|---|---|---|---|
| 多层意图路径 | 规则、检索、记忆与兜底分别何时接管 | 一个最终意图入口，候选和决定分开 | 原生产阈值、真实训练分布 | 未知/否定/缺槽反例与调用计数 |
| 多轮记忆 | 消息属于哪个问题，旧事实是否仍有效 | 事实库、问题生命周期、派生投影 | 原系统完整数据与运营策略 | 交错问题、补槽、更正、重投 |
| SOP 与工具执行 | 动作如何获得参数、证据和许可 | 受控工具循环与明确审批 | 企业真实下游 | 缺槽零工具、未批准零副作用、UNKNOWN 对账 |

这张表的价值在于暴露“不知道”。不了解原始阈值，就用开发集校准并标明数据规模；没有真实企业接口，就把协议实测与合成业务效果分开；使用替代模型的向量，就记录新的签名而不是声称处在原模型空间。

对陌生代码库，等价的第一步不是重写 README，而是找到一条实际请求：入口、领域值、主要用例、数据库/外部调用、异常和测试。用现有行为建立基线，先证明“它现在怎样工作”，再决定“我要怎样改变”。

### 3.2 P00 的任务是压缩环境不确定性，不是抢先做企业平台

早期 P00 将环境初始化单列，是合理分解。否则业务实现失败时，模型接口、数据库权限、隧道、版本兼容、代码逻辑混在一起，定位成本会很高。

但 P00 也应有退出条件。连接/协议探针只证明它检查的范围；没有必要为了开始学习就实现完整的企业高可用、所有环境完全对等或所有供应商适配。当前 P00 交接明确区分了历史 full 验收、只读 health、合成向量、未做整机重启等边界。[P00](../handoffs/P00.md)

可复用的顺序是：确认操作范围与已有资产，做最小真实协议探针，记录版本和必要恢复入口；只对本阶段必需的故障修复。不要每次遇到业务失败都重建基础设施，也不要把“重新初始化一个空环境后成功”当成原数据已恢复。

### 3.3 模块按可验证能力拆分，接口只冻结到足够协作

好的模块不是“写完一批文件”，而是回答一个可被观察的问题。例如 M05 应证明版本化语料能正确导入、续跑和检索；它不必同时决定最终意图。M11 可以先证明事件归属，再由 M12 接入完整主链。这样的边界既降低单次上下文负担，也能防止每个会话各造一套 DTO 或引擎。

每个模块至少需要目标、直接前置、输入输出、不变量、最小反例和完成条件。已有清楚的设计时直接实施；遇到接口空白或跨系统风险才补短 PLAN。早期 AGENTS 已写明“已有 PLAN 就实施，不继续拆 Prompt”，因此方法不是无限 Plan-and-plan，而是 **Plan-and-execute，执行反馈再修订计划**。[早期约定][C02]

“唯一领域类型”是协作基础，但不等于一开始冻结所有未来接口。先固定当前消费者需要的契约，实际变化通过版本和回归证明；过早写满巨型契约，会把还没被运行验证的假设变成维护负担。

### 3.4 越早得到纵向闭环，越早得到高质量反馈

初始包要求到 M08 固定首个可运行 MVP，而不是 22 个模块做完才运行。这个选择非常关键：用户输入经过清洗、意图、工具到事实回复和账本，第一次把模块之间的误解暴露出来。

M08 之后再加入混合检索、复杂归属、审批、可视化和发布治理，有一个共同参照物：新增能力有没有改变原来的事实、幂等和失败边界。后续调试不再面对一堆“分别写完但从未连接”的模块。[M08 提交][C04]、[当前状态](PROJECT_STATE.md)

## 四、1 到 n：把新会话当作隔离单元，把仓库当作交接介质

### 4.1 新会话隔离的是噪声，不应该隔离必要事实

作者用轻模型调度、每个 M 新开强执行会话，方向是对的。一个会话只承担一个有边界的模块，比长期携带所有安装日志、模型目录、测试输出、废弃方案，更容易保持当前目标清晰。

但“新会话”不是可靠性的充分条件。新会话可能丢失未完成状态，也可能读入过期规则；把同一套巨型文档在每个会话重读一遍，只是反复缴纳上下文成本。OpenAI 的官方说明也把项目指令视为按目录发现并合并的上下文，且存在总大小限制；这支持分层和精简，而不支持把全部历史不断追加到 AGENTS。[O01]

本项目当前读取规则值得保留：先看 Git/工作区、STATE、ROADMAP、当前规格、直接前置交接和相关代码；接口变化才读 CONTRACTS，来源争议才查对应 PDF 页。成功测试读摘要，失败只展开必要诊断。**执行测试所需计算量，与把测试输出注入模型所需上下文，是两回事。**[AGENTS](../AGENTS.md)

### 4.2 一 M、一主写者；M 内可以有多个特性闭环

`25b2d54` 的规则修订不是小修辞。旧规则是每次只实现一个特性、未另行启动不继续；它与作者“这个会话完成整个 M”的意图有冲突。新规则把 M 内全部未完成特性纳入同一会话的顺序授权，同时保留每个特性的验收和 Git 交付边界。[规则差异][C15]

可复用的粒度是：**M 用来管理学习目标和上下文，特性用来管理变更与验收，提交用来管理可追溯代码状态。** 三者不用强制一一对应。一个 M 内分两三个可独立验证的特性，通常比最后提交一个巨大、无法定位失败的改动更容易接手。

同一工作区不应该由多个写者同时切分支、更新根锁或改同一迁移。额外模型的价值优先放在固定提交的只读审查上；需要并行实施时必须明确隔离工作区与集成责任，不能把多 Agent 数量当作进度。

### 4.3 会话、特性、M、部署，分别定义完成

当前项目已有不少有效状态标记，但跨会话流程最好显式区分：实现完成、离线通过、真实内容通过、已提交、已合入、已同步、已安装。一个模块可以源码通过但不需要云安装；一个纯文档任务不该为获得 DONE 被迫重新运行模型。

一个简洁的交接记录可以采用下面的信息结构。它是方法示例，不是仓库现有 schema，也不建议另建一套与 STATE/handoff 重复的常驻日志。

```text
目标：当前 M 及规格基线；本次特性与剩余特性
代码状态：基线、工作分支、已提交 SHA、未提交文件及其拥有者
验收状态：已执行命令与结论、证据位置、适用版本、未执行项
交付状态：特性远端 / main 远端 / 本地同步分别处于哪一步
外部状态：正在运行的进程或操作、可能已发生的副作用、预算
续跑入口：下一条应该检查什么，再执行什么；禁止重复什么
```

其中最重要的不是写得多，而是让接手者能判断“恢复旧任务”还是“开始新任务”。一次中断不能让所有已验证结果作废；一次成功摘要也不能把还没提交的工作伪装成已交付。

### 4.4 全局审查应消除真实缺口，不成为新增 M 的生成器

作者在阶段结束后让 Astra 全局审查，是合理的角色分工：执行模型专注局部，把系统性命名、结构、依赖、教学路径、部署差异交给阶段审查。

但全局审查需要输入和输出边界。输入应是固定快照、最近变化、已知失败、学习目标，而不是“还有什么能做”；输出应是值得修复的少量缺口、保留现状的理由、可删除对象的证据和验收条件。否则模型总能提出新的可观测性、缓存、抽象层或框架替换，项目会无限扩张。

M32–M39 的高价值在于逐渐回到学习目标：同一引擎、Java 课程、原 run 解释、无旧环境启动、关键时序讲解及清理。最终 `f70784c` 又收敛了 AGENTS、状态、路线、安装说明等多份文档，说明治理不应只有“加规则”，还应有“把规则归位、删除重复”。[最终文档收敛][C25]

**后续约定（2026-10-05）：** 上述专项是已完成的基线修复，后续不循环复制为“新增一批能力→全项目补讲解/补观测/大清理”。职责归位、详细Python/Agent中文说明、适用课程/前端学习与原运行观测、直接相关文件清理和文档同步，随每个feature一起交付。M只拆新增、可独立验证的用户能力；实际编码/收尾要求统一维护在[AGENTS](../AGENTS.md#每个feature的编码与交付习惯)，后续规格见[ROADMAP](ROADMAP.md#后续能力规格)。这条后续约定不改变本报告对原固定基线和历史交接的评价。

## 五、失败复盘：不要把所有卡住都归因于模型不够聪明

### 5.1 已有证据的事件与可迁移修复

| 事件 | 已核对的事实 | 提炼的方法，而非扩大结论 |
|---|---|---|
| M05 Milvus 重启失败 | 内嵌 etcd 未就绪，`etcdserver: leader changed`、退出 134；交接判断非 OOM。冷备后独立同版本 etcd 复用原元数据，再验证原记录和向量 hash | 恢复的是原状态，不是新建空库；真实依赖探针不仅看健康，还看内容与重启后保真 |
| M05 客户端确认丢失 | 人工模拟 upsert 已发生而客户端未确认，保留 pending，同主键续跑；与真实服务崩溃分别记录 | 结果未知不等于没执行。记录动作身份，先查询，再决定重试 |
| M 的首特性完成后停下 | 旧规则限制一个特性；新提交明确一次“完成 M”覆盖模块内全部特性 | 先修复授权与完成语义，不能只在 Prompt 尾部增加“继续努力” |
| M39 Git 同步停住 | 已推送 `5500ea8` 后 pull 报 `Cannot fast-forward to multiple branches`；FETCH_HEAD 同时有两个可合并项，旧规则要求停止 | 故障要变成可恢复状态；核对跟踪分支后显式同步，避免盲目重复 pull、commit 或 merge |
| M19 分层后的测试和构建失败 | 超时测试还 patch 旧的隐式子进程参数；首次工具包 sdist 缺外部数据 | 重构要验证真实消费者和独立安装，不能仅在开发目录 import 成功 |
| Windows 通过、Linux 类型检查失败 | `subprocess.CREATE_NO_WINDOW` 在 Linux 类型环境不存在；改显式平台分支，未压制 mypy | 操作系统分支要在目标类型环境验证，不能以本机通过代替跨平台通过 |
| 新克隆无法启动本地课程 | M37 的干净目录安装被不存在的前端 built 阻塞；只对源码 editable 学习路径允许缺前端，正式 wheel 仍要求完整资源 | 本地核心学习和正式分发的契约不同；缩小学习依赖，不降低正式包完整性 |
| Rerank 接入了但收益不足 | dev 有提升；test Hit@1/MRR 持平，一条修复同时一条退化，延迟增加，默认保持关闭 | 工程接通、协议正确、质量收益是三项不同验收；负面结果也应该能正常交付 |
| 清理过程被策略拒绝或对象用途未知 | M37 如实保留未删临时环境；M39 后续核对后另记清理结果；未核对云消费者的对象保留 | 不把“打算删除”写成已删除；不绕过工具策略；某对象不能清理，不妨碍其他合法独立任务继续 |

来源：[M05](../handoffs/M05.md)、[M19](../handoffs/M19.md)、[M31](../handoffs/M31.md)、[M37](../handoffs/M37.md)、[M39](../handoffs/M39.md)、[M 范围修订][C15]、[Git 恢复修订][C23]。

M39 的恢复尤为典型：先确认 main 的跟踪配置和真实远端，再以不写共享 FETCH_HEAD 的 fetch，配合显式 `origin/main` 快进，恢复尚未成功的同步步骤。这不是建议在所有 Git 错误时机械执行同一段命令，而是示范“根据实际状态选择恢复路径”。冲突、鉴权失败和远端并发更新的处理不能照抄这个案例。[C23]

### 5.2 安全性与持续推进不是二选一

早期规则的合理意图是“不伪报成功、不乱改环境”；问题在于把多种不同故障统一映射为“停止会话”。可修复的格式错误、暂时网络错误、Git 状态异常，与没有权限、不可逆业务风险、缺少必要输入，不应走同一种路径。

更合适的分类是：

| 情况 | 处理原则 |
|---|---|
| 范围内代码、测试、格式或已授权 Git 问题 | 定位、修复、复验，从未成功步骤继续 |
| 外部动作结果未知 | 保留 UNKNOWN；查询账本、远端提交或操作状态，避免重复副作用 |
| 真实权限不足、敏感资产归属不清、工具策略拒绝 | 保留现场并说明缺项；不绕过权限，也不宣称已完成 |
| 环境暂不可达但不影响独立的分析或文档任务 | 继续可独立完成的部分，清楚标注未完成边界 |

**可持续闭环不是永不停下，而是停下后有准确状态、有下一步，且不会重复做危险动作。** 新规则不应该靠取消验收来提高完成率；应该靠扩大已授权、可验证的修复能力来减少无意义的人工接力。

### 5.3 模型切换的两类问题必须分开

作者描述的第一类是**写代码的会话更换模型或被打断**。本轮没有原始运行日志，无法确认具体中断机制。方法上的应对是：尽量在特性验收/提交边界切换；不得假设切模型会自动暂停所有子进程；交接前核对活动任务、工作区和最后成功步骤。恢复后先对账，而不是把原 Prompt 从头再执行一次。

第二类是**应用运行时更换 Chat、Embedding 或 Rerank 模型**。这是产品行为变化，不是换一个“更聪明的程序员”。需要核验协议、schema、工具选择、解析与事实质量；Embedding 签名变化要评估重索引，发布清单也要更新。不能因为供应商 API 名字相似就沿用旧质量结论。当前 AGENTS 和完整发布约束已对这类变化设置了边界。[AGENTS](../AGENTS.md)、[M31](../handoffs/M31.md)

## 六、把轻量调度做可靠：轻的是决策负担，不是状态管理

作者用轻模型调度、强模型执行，是合理的资源分工；但模型档位与调度正确性没有直接保证关系。轻模型可以选下一任务、读简要交接、解释阻塞；事实状态最好由可以重复运行的检查获得。

下面是对未来类似项目的设计建议，**不是声称当前 DeepHelp 调度器已经实现，也不是本次新增调度任务**。官方文档也区分本地项目任务与网页任务，并指出本地任务依赖电脑和应用处于可运行状态；定时触发本身并不提供完整的工程恢复语义。[O02]

### 6.1 把业务状态和交付状态分开

可采用这样的概念状态：

```text
READY -> RUNNING -> IMPLEMENTED -> VERIFIED
      -> COMMITTED -> MERGED -> SYNCED -> DONE

任何阶段可以进入：
RECOVERABLE_ERROR / WAITING_EXTERNAL / INTERRUPTED_UNKNOWN
恢复时回到最后已确认的阶段，而不是一律 READY。
```

这里的 VERIFIED 是当前任务要求的验收，不默认等于 live；SYNCED 是项目规定的目标同步范围，不等于已经部署。代码状态、实际安装、业务运行和学习掌握分别记录，避免一个 DONE 抹掉所有边界。

### 6.2 调度器的五个最小责任

**前置检查。** 根据规格版本和依赖能力选择下一 M；已部分实现时先补缺口，不重复生成。最早的编号不一定是最早可执行的任务。

**单写者控制。** 记录工作区、任务拥有者和活动执行。心跳超时只说明需要检查，不证明原进程已结束；不能马上启动第二个会话去修改同一工作区。恢复前核对进程和 Git 状态，必要时明确移交执行权。

**阶段对账。** 进程正常返回不等于验收 PASS，模型最终答复不等于 push 成功。对照产物、测试结果、commit 和目标远端，更新阶段。

**失败分类与续跑。** Git push 返回未知时先读远端；只重试未确认成功的动作。内容断言失败不能靠网络重试解决，缺权限不能靠换工具解决。

**有限通知。** 真正需要人的选择才打断；通知中给出最后成功阶段、错误类别、保留资产和下一步。不要只说“失败了，请继续”。

实现上不必一开始就引入复杂工作流平台。对单人串行工程，一个结构明确的任务状态、可核验的交付脚本和一个主写者约束，可能已经足够。只有实际证明现有机制不足，再增加租约、事件日志或更强调度系统。

### 6.3 Git 的可迁移原则与本仓库约定要区分

本仓库采用特性分支、中文提交、非快进合并、再把特性分支同步到合并点，并核对六个 SHA。这是当前项目的明确约定，应遵守。

但普适方法不是“所有工程都必须六 SHA 相同”，而是：**已验收变更与最终交付可追溯，预期远端确实可见，不能夹带未知修改，失败能从正确步骤恢复。** 团队可能采用 PR、分支保护或不同集成方式；不能将单人流程的所有往返机械复制过去。

当前约定不在 main 重复执行验收，能避免重复模型消费；前提是合入的内容仍对应已验证行为。基线改变或冲突解决改变行为时，应回到特性分支做受影响验证，不以“main 只保存”跳过新的风险。[AGENTS](../AGENTS.md)

## 七、易读学习型项目：把解释嵌入真实机制，而不是覆盖代码表面

### 7.1 当前代码里已经存在的好例子

在 [Conversation 编排](../modules/deephelp-app/src/deephelp_app/application/conversation/orchestrator.py) 中，中文说明先交代输入、输出、事实权威和阅读顺序；正文又在重要边界解释为什么先授权 hint、为什么未领取执行就返回 receipt、为什么主意图只在 600 进入、为什么缺槽不能派发工具。

这类注释不是把 `if` 翻译成中文，而是在解释**不能交换的顺序和不能破坏的不变量**。新读者能据此提出反例：先查 receipt 再授权会怎样？同一 message 重投为什么不能重新调用工具？有类别但缺参数，与无法识别类别有什么不同？

在 [终态保存](../modules/deephelp-app/src/deephelp_app/application/conversation/terminal.py) 中，`finish_run` 先落账，再记录诊断；短保存 Task 有时间边界，`shield` 只保护保存，不授权继续模型和工具。代码还说明第二次取消或进程强杀不在其提交保证内。这比笼统写“防止取消丢数据”更准确，也更适合从 Java 迁移到 Python 异步的读者。

在 [审批反例](../modules/deephelp-app/tests/unit/approval/test_m15_approval.py) 中，`test_unknown_queries_before_any_redispatch` 明确断言：UNKNOWN 先 query；确认 ABSENT 才 execute；不可达仍保持 UNKNOWN，不能提交成功；成功后再次 resume 不增加调用。测试观察的是原服务的动作顺序和状态，而不是复制一遍实现逻辑来获得通过。

这三个例子共同说明：**源码、反例和课程应互相指向，读者能从一句解释回到一个可执行断言。**

### 7.2 清楚不等于完全没有复杂性

当前主编排依然很长，包含较多嵌套分支，并把职责模块函数绑定为类方法；对 Python 新读者，这种组织仍有额外理解成本。抽样也能看到 application 对部分具体适配器类型的引用，因此不能仅凭目录名宣称已经达到严格的依赖倒置架构。

这不等于必须马上再拆一轮。下一次重构应以读者实际卡住的位置或测试隔离困难为依据：能否不展开多个适配器就解释一条路径？是否难以替换依赖？是否一个改动牵连多个无关用例？只有这些问题出现，才值得增加抽象。为了目录漂亮而增加更多层，同样会降低可读性。

### 7.3 学习入口、实验和真实部署应该复用同一引擎

当前课程有 14 章、11 个离线 topic，面向 Java 经验与 Python/Agent 初学背景，内容包含前置、类比边界、反例和源码导航。默认实验使用固定响应、向量、合成资料与内存适配器，但复用同一 Conversation、HybridRetriever、ApprovalService 等核心。它证明机制，不冒充真实模型质量或 PostgreSQL 跨进程持久性。[课程](learning/README.md)

本地核心路径不要求 Node、云凭据和本机完整中间件；云端完整工作台承担真实模型、持久历史、独立服务和观测教学。M37 还用没有旧 `.local` 的独立源码目录证明了这条路径，而不是只在作者已有环境里成功。[M37](../handoffs/M37.md)

这是一条非常值得复用的原则：**按用途降低学习启动成本，不靠另写一套简化业务逻辑来制造易学假象。** 同时，正式 wheel 仍要求完整前端资源，说明降低学习门槛与保证分发完整性可以同时成立。

### 7.4 从陌生仓库起步时，先交付一条可讲清楚的路径

没有 PDF、只有陌生代码库时，建议先做一个“接手模块”，但不预设必须叫 M00：固定提交，运行一条既有测试或请求，画清调用与事实流，标出副作用、版本和错误；挑一个小变更，先写能失败的反例，再修改并验证。

接手成果应能回答：事实在哪儿，谁拥有资源，哪个函数是主决策入口，哪些东西只是投影或展示，恢复时哪一份状态有权威。当前 DeepHelp 的 [源码导航](learning/source-navigation.md) 就是这种入口：从消息而不是文件树开始，再按问题进入具体子系统。

## 八、文档与中间文件治理：压缩噪声，保留恢复能力

### 8.1 不同信息各有一个主要归属

| 信息 | 应当放在哪里 | 不宜怎样保存 |
|---|---|---|
| 协作、权限、交付和读取规则 | AGENTS | 每个 handoff 再复制一份最新规则 |
| 当前已实现状态、限制、安装区别 | PROJECT_STATE | 在所有 README 都维护一张可能过期的进度表 |
| 能力机制与验收选择 | ROADMAP / 模块规格 | 把旧执行队列永久当作新任务指令 |
| 本次仍未完成的步骤 | 简短 PLAN | 做完后仍与规格、handoff 三份重复维护 |
| 历史实际验证和恢复边界 | handoff + 必要证据 | 保存每轮完整输出、临时状态和重复总结 |
| 当前可执行命令 | LOCAL_SETUP / 包 README | 从历史交接拼出当前启动方式 |
| 历史为什么改变 | Git / 关键决策 | 在每份常驻文档展开全部过去 |

当前最终文档整理已经朝这个方向收敛。它的作用不仅是让人阅读方便，也减少新会话把旧规则误当最新指令的概率。[C25]

### 8.2 `.gitignore` 不等于“不重要”

忽略文件可能包含不可提交的凭据，也可能包含唯一恢复资料、运行状态、预算、模型能力索引、发布资产、待审批绑定或调度状态。它们不应进入 Git，但不能因此随意删除；反过来，被 Git 跟踪的文件也不一定值得永远保留。

清理应先分类为：当前运行依赖、不可重建原件/证据、可重建缓存、被最终结果覆盖的过程副本、用途未知对象。删除依据是消费者、重建方式和恢复价值，不是文件年龄、大小或 M 编号。

M39 是有代表性的案例：受控文件只删除了已完成且由规格/交接覆盖的计划；忽略与临时对象历史记录合计删除 13,487 个文件、340,929,947 字节，同时对 1,245 份保留文件做前后 hash 核对。数字本身不是成绩，真正有价值的是保留依据、目标存在性检查和保护对象未变。没有读取当前云消费者的对象被保留，而不是顺手清空。[M39](../handoffs/M39.md)

清理操作还必须遵守工具权限。策略拒绝不能通过换工具、伪装命令或掩盖对象来绕过；未删就写未删。合法地重新界定任务范围，与规避同一个安全限制，是两回事。

### 8.3 少制造过程垃圾，比事后大清理更好

短期脚本和安装副本应从生成时就知道生命周期：由哪个任务创建，谁在使用，什么证据提取后可删。成功输出尽量只保存必要摘要；失败保留足够定位和恢复的上下文；正式 manifest 绑定的内容不能随手改写或用新摘要覆盖。

也不必为了清理再建立复杂的永久清理系统、每日扫描、无限归档目录。当前 AGENTS 已强调精确路径、资源退出后再删、未知对象单独保留；本报告不建议为这次复盘新增后台任务。[AGENTS](../AGENTS.md)

## 九、模型分工：保留角色经验，避免把它写成永恒能力排名

作者的使用模式可概括为：GPT 6 Pro 做最初问题建模与路线拆分，GPT 6.1 Sol 极高做高强度实施，轻档模型调度，Astra 极高阶段性审查和重规划。模型名称与档位来自作者陈述和历史讨论摘要；这是一套有效的个人经验，不是本报告独立完成的模型横向实验。

值得推广的是角色，而不是型号：

| 角色 | 适合交给它的问题 | 输出验收 |
|---|---|---|
| 规划者 | 来源不完整、目标冲突、跨系统取舍、最小路径 | 范围、前置、关键决策、可验证退出条件 |
| 实施者 | 边界清楚的代码、测试、调试与交付 | 实际产物、失败修复、可核验证据和 Git 状态 |
| 审查者 | 局部正确但整体复杂、教学断点、过期资产与结构债 | 有证据的缺口，不重复制造规划层 |
| 调度者 | 哪个任务可开始、是否需要恢复、是否真的交付 | 少量结构化状态与明确下一步 |

更换角色或模型时，优先在检查点切换；不要为了节省一点调用成本，把一个正在执行、尚未落账的任务交给不了解现场的新会话。也不要因规划模型的输出更宏大，就不断重规划已经足够清楚的工作。

项目今后可以记录少量可比较指标：从启动到验收的耗时、人工干预次数、恢复成功率、首次验收失败的类别、同类任务的返工量。统计时按任务难度和权限条件分组，否则“某模型更慢”可能只是它承担了更难的任务。没有这组记录前，维持个人偏好完全合理，但不宜给出伪精确的通用性能结论。

## 十、三个可直接复用的任务模板

这些模板用于下一次明确启动的任务，不改变本项目当前规则，也不要求把本文整篇塞入上下文。

### 10.1 从 PDF 或陌生代码库建立最小路线

```text
目标是可运行、可解释、可验证的学习项目，不是表面覆盖所有功能。
先区分来源事实、现有代码行为、未知信息和工程替代。
固定基线，找到最短纵向请求路径；列出必需环境、唯一事实源和关键副作用。
只拆当前阶段必要模块：每项给直接前置、输入输出、不变量、反例和退出条件。
明确第一条什么时候可以运行，哪些能力暂不做。
已有清楚计划不重复拆解；输出能被实施会话直接接手的最小上下文包。
```

### 10.2 完成一个 M，并能从中断恢复

```text
按当前 AGENTS 和 M 规格完成全部未完成特性，不自动进入其他 M。
先检查工作区、分支、规格版本、已有交接与活动执行，区分新开和续跑。
每个特性完成实现、适用验收及规定 Git 交付后，再继续同 M 的下一特性。
范围内可恢复错误先定位修复；结果未知先对账，不重复已经成功的外部动作。
不覆盖用户修改，不绕过工具权限，不降低验收，不把部分完成写成 M 完成。
交接只写事实、证据、未执行边界和恢复入口；解释关键机制，不转储全部过程。
```

### 10.3 阶段审查与学习验收

```text
基于固定提交审查是否仍服务学习目标，不默认新增功能。
检查一条请求能否顺畅追踪，课程是否复用真实核心，新环境能否独立开始。
找出重复职责、过期指令和有明确消费者证据的可清理对象。
对每项建议说明问题证据、预期学习收益、最小修改和验收方式；也写明不必改什么。
最后给一个需要读者预测、解释、修改和验证的练习，而不只要求阅读文档。
```

### 最值得肯定的三点

**你不是把方向交给模型，而是不断纠正优化目标。** 从“复刻功能”到“代码容易读、原理能实验、云端可观察、本地能开始”，这些不是模型自发多写代码就一定能得到的结果。对应的结构、课程、工作台和 M37 修复，已经进入仓库而不是停留在聊天里。[C17]、[C18]、[C20]、[C21]

**你开始把失败看成协作系统的问题，而不只是某次回答不好。** “为什么只做完首特性就停”“为什么 Git 问题需要我手工接力”最终变成明确授权和恢复规则。它说明你能从具体卡点识别可复用的问题类别，这是比反复更换提示词更有价值的能力。[C15]、[C23]

**你愿意维护结果的可信度，而不是只追求漂亮完成率。** 项目没有把不确定 usage 写零、把缺失诊断编成解释、把重排接入自动包装为收益，也没有用删除测试失败来制造全绿。这些证据主要来自仓库产物，不能全部推断为你逐项亲自设计，但说明你建立的目标和验收环境容纳并保留了这些正确做法。[M19](../handoffs/M19.md)、[M31](../handoffs/M31.md)、[当前约定](../AGENTS.md)

因此，“我做得不错”是有依据的自我认可。即使大量代码由模型生成，任务边界、反馈节奏、取舍和交付制度仍是作者工作的组成部分。没必要用手写代码行数否定这些能力；同样也不必把这些能力等同于已经掌握每个实现细节。

### 最需要改进的四点

**把补丁式约定继续压缩成统一协议。** 一次故障加一条规则很实用，但长期会产生相互覆盖、例外过多和误停。以后新增规则时同时问：它属于授权、状态转换、恢复还是验收？能否替代旧条款？哪些应该由脚本或测试保证而非靠模型记住？最终文档收敛是正确方向，不宜再退回追加式治理。

**让 M 的规模服从验证和理解成本，而不只是窗口能否装下。** 能在一个上下文里写完，并不意味着人能有效审查。过大的提交可保留模块目标，但拆成更小的可验证特性。提交说明应记录行为和不变量变化，而不仅是“完成 M”。

**对新基础设施和新框架增加学习收益预算。** PostgreSQL、官方 saver、Langfuse、前端和云安装都有学习价值，但组合起来也明显增加维护与理解负担。以后每次加组件先说清要学什么、为什么现有实现不能满足、何时停止；不因为“更现代”就默认迁移。

**把持续优化的一部分时间改为独立预测与调试。** 模型很擅长不断生成新的完善点，作者很容易一直做项目负责人而迟迟不做学习者。每完成一个阶段，应至少有一次不看答案的行为预测、一次自己定位错误、一次小机制修改。这比再增加几个页面更能证明能力增长。

## 十三、下一阶段：把项目冻结成教材，再让自己通过它

建议将当前学习基线固定下来，不再仅因为审查模型“还能想到优化点”就开启新 M。固定的是学习参照物，不是禁止修复缺陷。下面的自测可在已有离线课程与测试中开展，不需要新增平台、自动任务或付费调用。

| 自测 | 要独立完成的事情 | 合格证据 |
|---|---|---|
| 一条消息的完整路径 | 从 API 讲到事实、600、SOP、终态，解释 message/question/run 的区别 | 不借助 AI 复述关键顺序；对缺槽、未知与重投预测正确，再运行核对 |
| 异步资源与取消 | 指出 Task、连接、线程/子进程由谁创建、等待和关闭，说明 shield 的边界 | 能解释取消不等于下游未执行；修改一个时序并用反例验证 |
| UNKNOWN 审批恢复 | 预测 SUCCEEDED、ABSENT、不可达三种 query 结果，以及未批准情形 | 对照原审批测试，说明何时允许 execute、何时必须保留 UNKNOWN |
| 检索与评测 | 解释候选召回、重排、按意图归并和最终确认的差异 | 能复述 M31 为什么默认关闭，设计未泄漏的新样例并说明指标边界 |
| 小范围独立变更 | 增加一个有实际意义的边界或调整一个受控策略，不改掉安全断言 | 先有反例，再有修改和相关验证，能解释取舍及潜在回归 |

可以让 AI 在自测后做审查和讲解，但先保留自己的预测。预测错误不是失败的学习；没有做过预测、只读了模型的正确解释，才最容易产生“看起来都懂”的错觉。

一条实用的停止规则是：**当下一次结构改造带来的理解收益，低于运行一个已有实验、解释一个反例或亲手修改一处机制的收益时，就先停止改造。** 当前项目已经很接近这个阶段。

## 结语

从一份陌生 PDF 开始，到有可运行机制、真实依赖验证、审批恢复、观测、课程和清理治理，DeepHelp 已经不只是一次生成代码练习。它体现了一套正在成形的工程方法：用规划确定边界，用执行取得事实，用审查消除偏离，用可恢复状态跨越会话，再用实验把产物转化为理解。

这套方法最值得保留的一句话是：**让 AI 持续工作，靠的不是要求它永不停止，而是让它每一步都知道完成了什么、还欠什么、为什么失败，以及怎样安全地继续。**

对作者而言，下一步不需要证明自己还能让模型写出更大的项目；更有价值的是证明，这个已经被自己组织起来的系统，正在成为自己能讲清、改动和迁移的能力。
